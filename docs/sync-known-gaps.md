# 동기화에 남아 있는 구멍

2026-09-21 기준. 실제로 데이터가 사라진 경로들은 고쳤지만, 아래는 아직 열려 있다.

## 1. 저장이 경쟁 조건에 열려 있다 (제일 큼)

`cloudSaveNow()` 는 서버를 한 번 읽어보고(SELECT) 문제 없으면 통째로 올린다(upsert).
그 두 동작 사이에 다른 기기가 저장하면 그대로 덮인다. 한 탭 안의 저장은
`cloudSaveInFlight` 로 줄을 세우지만, 기기끼리는 아무 장치가 없다.

**고치는 법** — `vr_data.updated_at` 을 표로 삼아 조건부 갱신(compare-and-swap):

```js
const { data } = await sb.from("vr_data")
  .update({ data: next, updated_at: nextToken })
  .eq("user_id", userId)
  .eq("updated_at", expectedToken)   // 내가 읽었던 그 값일 때만
  .select("updated_at");
// data.length === 1 이면 내가 이겼다. 0 이면 그새 누가 저장했다 → 다시 읽고 다시 판단.
```

주의할 점:

- 지금 SELECT 는 `data` 만 읽는다. `updated_at` 도 같이 읽어서 따로 들고 있어야 한다.
- `updated_at` 을 클라이언트가 만들어 넣고 있다. CAS 표로 쓰려면 서버가 돌려준
  값을 그대로 보관해야 한다.
- 행이 아직 없을 때는 INSERT 여야 한다. 그냥 upsert 하면 두 기기가 동시에
  만들 때 다시 뚫린다. unique 충돌이 나면 재조회 후 다시 판단.
- 0행(충돌)일 때 그냥 다시 올리면 안 된다. 최신 서버를 다시 읽고
  `recordCount`/`missingRecords`/백업 규칙을 처음부터 다시 태워야 한다.

**왜 아직 안 했나** — `test/stub.js` 의 `eq()` 는 인자를 무시하고 `update()` 는
실제로 아무것도 안 고친다. 검증할 방법이 없는 채로 동기화 경로를 건드리는 건
이 앱에서 제일 위험한 짓이다. 스텁에 아래 상황을 먼저 만들고 나서 손대야 한다:

- 조건부 update 가 1행/0행을 제대로 돌려주는가
- 두 기기가 동시에 update 했을 때 한쪽만 이기는가
- 행이 없을 때 두 기기가 동시에 insert 하면 어떻게 되는가
- 충돌 후 재조회 → 재판단 → 재시도가 무한루프에 빠지지 않는가

## 2. 총건수가 같으면 종류가 다른 기록끼리 상쇄된다

받아올지 말지는 아직 `recordCount` 차이로 정한다. 매매 37건이 빠지고 VR
사이클 37개가 늘어난 사본은 "같은 개수"라 묻지 않는다.

지금은 사라질 기록이 있으면 **묻지 않더라도 백업은 남기도록** 해뒀다
(`missingRecords`). 되돌릴 수는 있지만 알아채지 못할 수는 있다.

판단 자체를 `missingRecords` 로 바꿔봤다가 되돌린 적이 있다 — 서로 조금만
갈라져도 매번 물어서 쓸 수 없었다. 제대로 고치려면 "둘 다 상대에게 없는
기록을 갖고 있다"는 분기 상태만 충돌로 다루고, 한쪽이 다른 쪽을 포함하면
조용히 따라가야 한다.

## 3. 기기 시계에 기대고 있다

`stateAt(srv) > lastServerAt && stateAt(srv) !== stateAt(stateObj)` 가 거짓이면
서버 확인을 건너뛴다. 시계가 어긋난 기기가 섞이거나 두 저장이 같은 밀리초면
보호가 빠진다. 1번 CAS 로 옮겨가면 같이 없어진다.
