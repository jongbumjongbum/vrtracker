# 원화로 산 주식의 원가·손익을 정확히 남기기

날짜: 2026-09-13
상태: 설계 승인 대기

## 1. 왜 고치나

QLD를 증권사 "주식모으기"로 **원화로 적립 매수**하고 있다. 앱은 모든 금액을
달러로 저장하고, 원화 보기(₩ 버튼)는 저장된 달러 값에 **오늘 환율**을 곱해
보여줄 뿐이다 (`fmtCurrencyDigits`, `krwViewRate`). 그래서 두 가지가 깨진다.

**(1) 실제로 낸 원화가 어디에도 안 남는다.**
8월에 10만원(당시 1,300원/$)을 내고 산 물량의 원가는 $77로 저장된다. 환율이
1,400원이 되면 앱은 그 원가를 "10만 7천원"으로 보여준다. 실제로 낸 건 10만원
이므로 7천원은 앱이 만들어낸 숫자다. 결과적으로 **"원화 얼마 넣어서 원화 얼마
됐나"를 볼 수 없다.**

**(2) 지금은 표에서 수량만 직접 고쳐 기록하고 있다.**
직접 수정은 거래 이력(`h.trades`)을 남기지 않는다 → 매입평균가를 손으로 계산
해야 하고, 나중에 팔 때 실현손익이 계산되지 않으며, 투입한 원화 기록이 0이다.

## 2. 목표

- 원화로 산 매수 건은 **낸 원화 금액을 그대로 저장**한다.
- 종목별로 **원화 기준 손익**과 **달러 기준 손익**을 나란히 본다.
- 기존 흐름("매수/매도 기록 추가")을 그대로 쓴다 — 새 탭·새 모드 없음.
- QLD를 **총자산에서 빼지 않는다.** 실제 자산이므로 포함이 맞다.

### 하지 않는 것 (범위 밖)

- QLD 전용 탭 신설 — 종목 하나를 위해 6번째 탭을 만들 이유가 없다.
- **원화 기준 실현손익** — 지금은 매수만 하고 매도 계획이 없다. 매도 시에는
  원가만 비례 차감해 미실현 손익이 계속 맞게만 해둔다.
- 과거 환율 조회 — 무료 API로 일자별 환율을 안정적으로 받기 어렵고, 낸 원화를
  직접 적으면 애초에 환율이 필요 없다.
- 손익 탭 그래프·총자산 그래프의 원화 기준 전환 — 달러 기준 유지.

## 3. 기존 기록 처리

**현재 기록된 QLD 수량·평단은 맞으므로 건드리지 않는다.**

`manualHoldingSeed(h)`는 현재 수량·평단에서 거래 이력을 거꾸로 되감아 "거래
기록 이전의 출발 상태"를 만든다. 지금처럼 거래 기록이 하나도 없으면 현재
수량·평단이 통째로 출발 상태가 된다. 새 방식으로 기록하는 매수는 그 위에
쌓인다 — 기존 물량은 그대로 보존된다.

기존 물량에 넣은 원화 총액을 아는 경우에 대비해, 종목마다 **"기존분 원화 원가"**
를 한 번 적을 수 있는 칸을 둔다. 비워두면 원화 손익은 **앞으로 기록하는 매수분
에 대해서만** 계산하고, 화면에 그렇게 적어 알린다 (VR의 "실제평단 미입력분 제외"
와 같은 방식).

## 4. 데이터 구조

새 필드는 전부 **선택**이다. 없으면 지금과 완전히 같게 동작한다.

### 거래 (`holding.trades[]`)

```
{ id, date, type, qty, price, gain, krwAmount? }
```

- `krwAmount` — 이 거래에 실제로 낸(또는 받은) 원화. 원화로 사지 않았으면 없음.

### 보유 종목 (`state.portfolio.holdings[]`)

```
{ id, ticker, qty, avgCost, currentPrice, trades, realizedPL,
  krwSeedCost?, krwSeedQty? }
```

- `krwSeedCost` — 거래 기록 이전 기존 물량에 넣은 원화 총액.
- `krwSeedQty` — 그 원화에 대응하는 수량. `krwSeedCost`를 입력하는 순간의
  `manualHoldingSeed(h).qty`를 자동으로 넣는다 (사용자가 따로 적지 않는다).

### 예수금 변동내역 (`state.portfolio.cashLog[]`)

```
{ id, date, kind, amount, note, tradeId? }
```

- `tradeId` — 원화 매수와 짝지어 자동 생성된 입금 줄임을 표시. 해당 거래를
  수정·삭제하면 이 줄도 같이 따라간다.

### 기존 데이터 호환

`state.portfolio`를 정리하는 초기화 블록(index.html:1766 부근)에서 위 필드가
없으면 그대로 둔다. 기본값을 0으로 채워 넣지 않는다 — "입력 안 함"과 "0원"을
구분해야 화면에서 "미입력분 제외" 안내를 띄울 수 있다.

## 5. 계산 규칙

`computeKrwBasis(h)`를 새로 만든다. `replayManualHolding`과 같은 순서로 거래를
훑되, 원화 원가만 따로 센다.

```
seed   = manualHoldingSeed(h)
qty    = seed.qty                  // 전체 수량 (원화분 + 비원화분)
krwQty = h.krwSeedQty  || 0        // 원화 원가가 기록된 수량
krwCost= h.krwSeedCost || 0        // 그 수량에 대응하는 원화 원가

각 거래 t 마다:
  매수: qty += t.qty
        t.krwAmount 가 있으면  krwQty += t.qty,  krwCost += t.krwAmount
  매도: f = qty > 0 ? min(t.qty, qty) / qty : 0     // 평균단가 방식과 동일하게 비례 차감
        krwQty  *= (1 - f)
        krwCost *= (1 - f)
        qty     -= min(t.qty, qty)

반환: { krwQty, krwCost }
```

매도 시 비례 차감을 쓰는 이유: 앱은 이미 평균단가 방식으로 원가를 덜어낸다
(`replayManualHolding`). 원화 원가도 같은 규칙을 따라야 두 숫자가 어긋나지 않는다.

### 화면에 쓰는 값

```
원화 평가금 = krwQty × 현재가($) × 오늘환율
원화 손익   = 원화 평가금 − krwCost
원화 수익률 = 원화 손익 ÷ krwCost × 100
```

- `krwCost`가 0이면 원화 칸은 `–`로 두고 아무것도 계산하지 않는다.
- `krwQty < qty`이면 "원화 원가 미입력분 제외"를 덧붙인다.
- 환율(`state.fx.usdkrw`)이 없으면 원화 평가금을 계산할 수 없으므로 "환율
  새로고침 필요"로 표시한다.

## 6. 예수금 처리

이게 이 설계에서 제일 조심할 부분이다.

지금 `mutateManualTrades(h, mutate)`는 거래 목록을 바꿀 때마다 순현금효과만큼
`extraCash`를 움직인다. 즉 **$77 매수를 기록하면 그외 예수금이 $77 줄어든다.**
그런데 QLD는 달러 예수금이 아니라 **밖에서 새로 넣은 원화**로 사는 것이라
예수금이 줄면 안 된다.

해결: `krwAmount`가 있는 매수를 기록할 때 **같은 금액의 입금 줄을 자동으로
같이 남긴다.**

```
매수 기록    → extraCash −= qty × price
자동 입금 줄 → extraCash += qty × price     (pushCashLog + extraCash 직접 가산)
합계          → 0 (예수금 그대로)
```

- 입금 줄의 메모: `"QLD 원화 적립 ₩100,000"`
- 입금 줄에 `tradeId`를 달아 거래와 묶는다. 거래를 고칠 때는 네 경우를 모두
  처리한다:

  | 고치기 전 | 고친 뒤 | 해야 할 일 |
  |---|---|---|
  | 원화 없음 | 원화 있음 | 입금 줄을 새로 만든다 |
  | 원화 있음 | 원화 있음 | 입금 줄의 금액·날짜·메모를 고친다 |
  | 원화 있음 | 원화 없음 | 입금 줄을 지운다 (예수금이 매수액만큼 줄어든다) |
  | (거래 삭제) | — | 입금 줄도 같이 지운다 |
- 이 방식은 **자동 검사기의 예수금 불변식을 그대로 만족한다** —
  "그외 예수금 = 입출금 + 직접입력 매매 + 무매 매매 + VR 적립·인출". 자동 입금은
  가짜 보정이 아니라 진짜 입출금 줄이므로 양쪽에 똑같이 잡힌다.

부수 효과로 예수금 변동내역에 "QLD에 원화를 얼마 넣었나"가 날짜순으로 쌓인다 —
투입 원금 추적이 덤으로 해결된다.

## 7. 화면 변경

### (1) 매수/매도 기록 추가 폼 (index.html:3985 부근)

칸을 5개에서 6개로 늘린다.

```
종목 │ 구분 │ 수량 │ 가격($) │ 낸 원화(₩) │ 날짜
```

- `낸 원화`는 선택 입력. 비워두면 지금과 100% 동일하게 동작한다.
- 안내: "원화로 샀으면 실제 결제된 원화를 적어주세요. 적으면 예수금은 그대로
  두고 원화 기준 손익을 계산해요."
- 구분이 `매도`면 비활성화한다 (원화 실현손익은 범위 밖).

### (2) 직접 추가한 종목 표 (`renderManualHoldingsTable`, index.html:5045)

칸 두 개를 더한다: **원화 원가**, **원화 손익(수익률)**. 원화 원가가 없는
종목은 둘 다 `–`.

원화 원가가 있는 종목은 티커 옆에 `₩적립` 뱃지를 자동으로 붙인다. 별도 입력
없이 적립식 종목이 눈에 구분된다 — 탭을 나누지 않고도 원하던 구분이 된다.

### (3) 기존분 원화 원가 입력

종목 행을 펼쳤을 때 나오는 영역에 칸 하나. 안내: "이 앱에 매수 기록을 넣기 전
이미 갖고 있던 물량에 들어간 원화 총액. 모르면 비워두세요."
저장 시 `krwSeedQty = manualHoldingSeed(h).qty`를 같이 넣는다.

### 총자산 통계

**바꾸지 않는다.** 총자산·도넛·손익 탭은 지금 그대로 달러 기준으로 둔다. QLD는
총자산에 계속 포함된다.

## 8. 검사

`test/fuzz.js`의 불변식에 두 줄을 더한다.

- **원화 원가가 음수가 되지 않는다** — 매도 비례 차감이 과하게 깎지 않는지.
- **원화 원가가 기록된 수량(`krwQty`)이 전체 수량(`qty`)을 넘지 않는다** —
  넘으면 어딘가에서 이중으로 세고 있다는 뜻.

기존 예수금 불변식은 그대로 둔다 — 자동 입금 줄이 진짜 입출금이라 손댈 필요가
없다. 오히려 이 불변식이 6절 설계가 맞는지 검증해 준다.

손으로 확인할 것:

1. 원화 칸을 비운 매수 → 예수금이 매수액만큼 줄어든다 (기존 동작 유지).
2. 원화 칸을 채운 매수 → 예수금이 그대로다. 변동내역에 입금 줄이 생긴다.
3. 그 거래를 삭제 → 입금 줄도 같이 사라지고 예수금이 원래대로 돌아온다.
4. 원화 매수 2건 후 원화 손익 = (수량 × 현재가 × 환율) − (낸 원화 합계).
5. 기존분 원화 원가를 넣으면 그 물량까지 원화 손익에 포함된다.
